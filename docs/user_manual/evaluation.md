# 평가와 튜닝

이 문서의 내용을 건너뛰고 싶은 마음이 들 겁니다. 골든셋 라벨링은 지루하고,
당장 리뷰는 돌아가니까요.

그런데 골든셋이 없으면 룰을 추가했을 때 좋아졌는지 나빠졌는지 알 수 없습니다.
필터가 실제로 도움이 되는지도 모릅니다. 컨텍스트 상한을 올려도 되는지도 모릅니다.
그냥 감으로 만지게 되고, 감은 대체로 틀립니다.

일주일만 쓰세요. 그 뒤 모든 판단의 근거가 됩니다.

이 문서는 골든셋을 *어떻게* 만들고 지표를 *어떻게* 읽는지를 다룹니다. 전체 도입
순서에서 이게 어디에 놓이는지는 [워크플로](workflow.md#도입-순서)를 보세요.

## 지표 셋

**KBI (Key Bug Inclusion)** — 실제 결함 중 몇 개를 잡았나. 재현율입니다.

**FAR (False Alarm Rate)** — 내보낸 지적 중 몇 개가 헛다리였나. **이게 최우선
관리 지표입니다.** 재현율이 아니라 이쪽입니다.

오탐 하나는 놓친 결함 하나보다 비쌉니다. 놓친 결함은 원래 하던 리뷰가
잡을 여지가 남지만, 오탐은 멀쩡한 코드에 사람의 시간을 쓰게 하고, 틀렸다는
판정을 내리려면 어차피 전부 읽어야 합니다. 지적 수가 적더라도 하나하나가
맞는 편이 낫습니다.

**룰별 정밀도** — 어떤 룰이 오탐을 만드는지. 폐기 대상을 고르는 근거입니다.

## 골든셋 만들기

```bash
python eval/run_eval.py init
```

`eval/golden/` 과 템플릿이 만들어집니다.

### 사례 고르기

과거 MR 50~100건을 고릅니다. 기준은 이렇습니다.

- **리뷰어가 실제로 결함을 지적한 MR** 을 우선합니다. 아무 지적 없이 승인된
  MR 만 모으면 KBI 를 잴 수가 없습니다.
- C++/C#/Python 을 균등하게 섞습니다. 한 언어에 몰리면 나머지 언어의 룰을
  튜닝할 근거가 없어집니다.
- 너무 큰 MR 은 피합니다. 파일 50개짜리 리팩터링은 라벨링이 지옥이고 평가
  시간도 오래 걸립니다.
- 그렇다고 오탐 확인용으로 **깨끗한 MR 도 20~30% 섞으세요.** 결함이 하나도 없는
  변경에 도구가 뭐라고 하는지가 FAR 의 핵심입니다.

### diff 저장

각 사례의 diff 를 파일로 남깁니다.

```bash
git diff <base> <head> > eval/golden/diffs/mr-1234.diff
```

`<base>` 는 병합 기준점입니다. `git merge-base main <head>` 로 구하세요.

### 저장소 스냅숏

여기서 많이들 막힙니다. CREX 는 diff 만으로 리뷰하지 않습니다. 코드 본문을
디스크에서 읽습니다. 그래서 **그 MR 시점의 코드가 있는 저장소 경로**가 필요합니다.

가장 간단한 방법은 사례별로 워크트리를 만드는 겁니다.

```bash
git worktree add ../snapshots/mr-1234 <head>
```

디스크가 아깝다면 평가 직전에 순차적으로 체크아웃하는 스크립트를 써도 됩니다.
다만 `on_mismatch = "raise"` 가 기본이므로, 체크아웃과 실행 시점이 어긋나면
그 사례는 오류로 기록되고 넘어갑니다. 조용히 틀린 결과가 나오지는 않습니다.

### 라벨링

`eval/golden/*.jsonl` 에 한 줄에 한 사례씩 씁니다.

```json
{"case_id": "mr-1234", "repo_path": "D:/snapshots/mr-1234", "diff_path": "eval/golden/diffs/mr-1234.diff", "note": "raw 포인터 무효화", "defects": [{"path": "src/buffer.cpp", "line": 16, "category": "code_defect", "severity": "high", "comment": "resize 이후 포인터 무효화", "expected_rule": "cpp.dangling-after-realloc"}]}
```

`defects` 에는 **리뷰어가 실제로 지적한 결함만** 넣습니다. 여기가 라벨링의 전부이고,
여기서 흔들리면 모든 숫자가 흔들립니다.

넣지 말아야 할 것들:

- 칭찬 ("좋은 리팩터링이네요")
- 질문 ("이거 왜 이렇게 하셨나요?")
- 스타일 코멘트 ("변수명을 좀 더 명확하게")
- 설계 논의 ("이 클래스를 분리하는 게 어떨까요")

넣어야 할 것: **고치지 않으면 문제가 되는 것.** 그것만입니다.

`expected_rule` 은 선택입니다. 적어두면 나중에 "이 결함 유형을 잡는 룰이 있는데
왜 못 잡았지"를 추적할 수 있습니다.

결함이 없는 깨끗한 MR 은 `"defects": []` 로 둡니다. 이 사례들이 FAR 을 만듭니다.

빈 줄과 `//` 로 시작하는 줄은 무시하므로, 주석을 달아 정리해도 됩니다.

## 숫자 읽기

### 매칭 규칙

지적과 골든 결함은 **같은 파일, 라인 차이 3줄 이내**면 매칭으로 봅니다.
리뷰어는 결함 라인을 정확히 짚지 않고 근처에 코멘트하기 때문입니다.

허용 오차를 늘리고 싶은 유혹이 생길 텐데 참으세요. 넓히면 FAR 이 낙관적으로
나옵니다. 엉뚱한 지적이 우연히 근처 결함에 걸려서 정탐으로 계산됩니다.

같은 결함을 두 번 지적해도 재현율은 1건만 오릅니다. 중복으로 점수를 벌 수 없습니다.

### 기각률이 이상할 때

**40% 미만이면** 검증이 일을 안 하고 있습니다. 검증 모델이 무조건 yes 를 내고
있을 가능성이 큽니다. `reports/*.json` 의 `rejected` 를 열어 사유 분포를 보세요.
전부 `line_out_of_range` 같은 결정론적 기각뿐이고 `verdict_no` 가 거의 없다면
LLM 검증이 헛돌고 있는 겁니다.

**70% 초과면** 생성 쪽이 헛돌고 있습니다. 룰이 코드와 안 맞거나, 프롬프트가
잘려서 모델이 맥락 없이 추측하고 있을 수 있습니다.

### 룰별 정밀도

정밀도 50% 미만인 룰은 손볼 때입니다. 순서는 이렇습니다.

1. 그 룰이 만든 오탐을 JSON 에서 몇 개 읽어봅니다.
2. 공통 패턴이 보이면 `counter` 에 추가합니다.
3. 재측정합니다.
4. 그래도 안 오르면 뺍니다.

`emitted` 가 2~3건뿐인 룰의 정밀도는 신뢰하지 마세요. 통계적으로 의미가 없습니다.
10건 이상 나온 룰부터 판단하세요.

## Phase 별 수용 기준

| Phase | KBI | FAR | 청크당 지연 |
|---|---|---|---|
| 1 (베이스라인) | 측정만 | 측정만 | 측정만 |
| 2 (룰 적용) | ≥ 베이스라인 | ≤ 베이스라인 | — |
| 3 (필터 적용) | 베이스라인의 90% 유지 | **≤ 25%** | ≤ 10초 |

Phase 3 에서 KBI 가 좀 떨어지는 건 정상입니다. 의도한 겁니다.
필터가 애매한 지적을 걸러내면 재현율은 내려가고 정밀도는 올라갑니다.
그 교환을 하려고 만든 단계입니다.

## 리포트 비교

```bash
python eval/run_eval.py compare reports/phase-1.json reports/phase-3.json
```

```
phase-1.json  →  phase-3.json

  - KBI (재현율)     58.3% →  54.8%  (-3.5%)
  + FAR (오탐률)     19.4% →  11.2%  (-8.2%)
      필터 기각률     51.2% →  58.7%  (+7.5%)

    평균 소요          43.7s →   51.2s
```

`+` 는 좋아진 것, `-` 는 나빠진 것입니다. 위 결과는 재현율 3.5%p 를 내주고
오탐률 8.2%p 를 얻은 겁니다. 좋은 거래입니다.

## CI 게이트

```bash
python eval/run_eval.py run --max-far 0.25
```

FAR 이 25% 를 넘으면 종료 코드 1 입니다. 룰을 고칠 때마다 이걸 돌리게 해두면
오탐이 슬금슬금 늘어나는 걸 막을 수 있습니다.

## 그다음 — 플라이휠

골든셋은 만들기 비싸고 갱신도 비쌉니다. 그래서 운영 단계에서는 사람 손이 덜 가는
지표로 갈아탑니다.

### Outdated Rate

지적된 라인이 이후 커밋에서 실제로 수정됐는지를 봅니다. 1주 윈도우로 재고,
수정됐으면 그 지적은 "받아들여진" 것으로 봅니다.

수동 라벨링 없이 대규모로 잴 수 있는 유일한 실용 지표입니다. 인간 리뷰어의
기준선이 35~46%이고, BitsAI-CR 이 Go 에서 26.7%를 달성했습니다.

CREX 에는 아직 구현되어 있지 않습니다. 리뷰 결과 JSON 을 보관해 두고 나중에
`git log -L` 로 대조하는 스크립트를 짜면 됩니다. Phase 4 과제입니다.

### 좋아요/싫어요

리포트 하단에 반응을 남길 창구를 만들고 JSON 로그로 모으세요. 정교할 필요
없습니다. 주 단위로 룰별 집계만 나오면 충분합니다.

### 2주마다 룰 성적표

정밀도와 Outdated Rate 를 함께 보고 룰을 취사선택합니다. BitsAI-CR 의 기준은
14일 기준 정밀도 65%±5, Outdated Rate 25%±5 입니다. 이 밑으로 떨어지는 룰은
폐기 후보입니다.

정밀도가 높은데 Outdated Rate 가 낮은 룰이 특히 흥미롭습니다. **맞는 말이지만
아무도 고치지 않는 지적**이라는 뜻입니다. 대개 우선순위가 낮거나, 지적은 옳지만
고치는 비용이 큰 것들입니다. 이런 룰은 `severity` 를 낮추거나 빼는 게 낫습니다.
