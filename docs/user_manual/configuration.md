# 설정

`crex.json` 파일 하나로 모든 동작을 제어합니다. 설정 파일을 탐색하는 우선순위는 다음과 같습니다.

1. `--config` 옵션 또는 `CREX_CONFIG` 환경변수로 직접 지정한 파일
2. `--workspace` 옵션이나 환경변수로 대상 저장소를 지정한 경우 `<워크스페이스>/crex.json`
3. 현재 디렉터리에서 상위 디렉터리로 올라가며 `crex.json` → `.crex.json` 순으로 탐색
4. 위 경로에 모두 없으면 내장 기본값 사용

2번 규칙이 있는 이유는 저장소마다 `compile_commands_dir`이나 `dotnet_project` 경로가 다르기 때문입니다. CREX 설치본 하나로 여러 저장소를 리뷰할 때 각 저장소의 고유 설정을 자동으로 따라가도록 설계했습니다. 이때는 워크스페이스 루트 *내부*만 확인하며, 상위 디렉터리로 올라가 다른 프로젝트의 설정 파일을 읽어 오지 않습니다.

설정 키에 오타가 있으면 조용히 무시하지 않고 즉시 오류를 발생시킵니다. 예를 들어 `max_worker`라고 잘못 적으면 다음과 같이 안내합니다.

```
설정 오류: ReviewConfig 에 알 수 없는 설정 키: ['max_worker']. 사용 가능한 키: [...]
```

최상위 키도 마찬가지입니다. `workspase`처럼 오타가 나면 즉시 오류를 보고합니다 — 이를 조용히 무시하면 의도치 않게 리뷰 대상 저장소가 바뀌어 가장 위험하기 때문입니다.

## 주석과 여러 줄 글

표준 JSON은 주석과 여러 줄 문자열을 지원하지 않습니다. 그러나 설정 파일은 사람이 직접 읽고 수정하는 문서이므로, 표준 JSON 문법을 그대로 유지하면서 **두 가지 규칙**을 도입했습니다. 일반 JSON 파서나 편집기에서 열어도 문법 오류가 발생하지 않습니다.

**1. 키 이름이 `//`로 시작하면 설명(주석)으로 처리합니다.** 설정 검증 전에 자동으로 제거하므로 값에는 어떤 형식이든 넣을 수 있으며, 중첩 객체 어느 위치에서나 사용할 수 있습니다.

```json
{
  "// max_workers": "동시 LLM 호출 수. vLLM 서버의 배치 처리량에 맞춰 조정합니다.",
  "review": { "max_workers": 4 }
}
```

`"// max_workers"`와 `"max_workers"`는 **서로 다른 키**이므로 주석이 실제 설정값을 덮어쓸 염려가 없습니다.

일반 주석 문법과 비교했을 때 한 가지 큰 장점이 있습니다. 설명이 **JSON 데이터의 일부**로 취급되므로 프로그램이 설정 파일을 읽고 다시 저장해도 주석이 사라지지 않습니다. `python -m crex workspace <경로>`나 `python -m crex compiledb` 명령이 `crex.json`을 갱신해도 기존에 적어 둔 설명은 그대로 보존됩니다.

**2. 문자열 타입의 설정은 문자열 배열로 나누어 적을 수 있습니다.** 파일을 읽을 때 줄바꿈(`\n`)으로 이어 붙입니다.

```json
{
  "// min_severity": [
    "이 심각도 미만의 지적은 리포트에서 숨깁니다. 기각(rejected)과는 다릅니다 —",
    "유효하다고 판정된 지적을 현재 리포트에서만 표시하지 않는 설정입니다."
  ],
  "review": { "min_severity": "low" }
}
```

긴 문자열을 `\n` 이스케이프로 한 줄에 몰아 적으면 가독성이 크게 떨어집니다. 긴 설명이나 프롬프트는 배열을 사용해 줄 단위로 나누어 작성하십시오.

이 줄바꿈 병합 규칙은 **선언된 타입이 문자열(`str`)인 설정에만** 적용됩니다. `analyzers`처럼 원래 배열(`list`) 타입인 설정은 배열 그대로 유지됩니다.

```json
{
  "grounding": {
    "// analyzers": ["원래 배열 타입인 설정입니다.", "하나의 문자열로 합치지 않습니다."],
    "analyzers": ["cppcheck", "ruff"],

    "// clang_tidy_checks": "문자열 설정입니다. 배열로 적으면 줄바꿈으로 이어 붙입니다.",
    "clang_tidy_checks": ["-*,", "bugprone-*,", "cert-*"]
  }
}
```

### 예전 `crex.toml`이 남아 있다면

더 이상 읽지 않습니다. 다만 **조용히 무시하지도 않습니다** — 설정 파일을 수정했는데 아무런 변화가 없는 상황을 방지하기 위해, `crex.json` 없이 예전 `crex.toml`만 존재하면 실행을 멈추고 전환 방법을 안내합니다.

```
설정 오류: D:\tools\crex\crex.toml 는 더 이상 읽지 않습니다. 설정 파일은 JSON 으로 바뀌었습니다.
  crex.json 을 만들어 옮겨 적으십시오. 양식은 crex.example.json 과 docs/configuration.md 에 있습니다.
```

`crex.json`을 생성한 뒤에는 예전 파일이 남아 있어도 `crex.json`이 우선 적용됩니다.

## `workspace` — 리뷰 대상 저장소

```json
{
  "workspace": "D:/work/myrepo"
}
```

**CREX를 리뷰 대상 저장소 안에 둘 필요가 없습니다.** 설치본은 한곳에 두고(폐쇄망에서는 반입 심사를 통과한 원본 한 벌만 유지하는 것이 무결성 관리에 유리합니다) 리뷰할 대상 저장소만 가리키면 됩니다.

```
D:\tools\crex\        ← 실행 위치 (작업 디렉터리이자 CREX 모듈 위치)
D:\work\myrepo\.git   ← 리뷰 대상 저장소
```

```bash
cd D:\tools\crex
python -m crex review --workspace D:\work\myrepo --staged
```

파일을 직접 열지 않고 아래 명령으로 `crex.json`에 대상 저장소를 등록할 수도 있습니다.

```bash
python -m crex workspace                    # 현재 설정된 대상 저장소 확인
python -m crex workspace D:\work\myrepo     # crex.json에 대상 저장소 고정
python -m crex workspace --clear            # 고정 해제
```

경로가 실제로 존재하는지 먼저 검증한 뒤 기록하므로, 잘못된 경로가 설정 파일에 저장되어 다음 실행이 실패하는 일을 막아줍니다. 파일을 다시 쓸 때도 `"// ..."` 설명과 다른 설정값은 그대로 보존됩니다.

워크스페이스 결정 우선순위는 위에서 아래 순이며, 상위 항목이 지정되면 하위 항목은 무시됩니다.

| 우선순위 | 지정 방식 |
|---|---|
| 1 | 명령줄 옵션 `--workspace D:\work\myrepo` (이전 이름 `--repo`도 계속 지원) |
| 2 | 환경변수 `CREX_WORKSPACE` (이전 이름 `CREX_REPO`도 계속 지원) |
| 3 | `crex.json`의 `workspace` 항목 |
| 4 | 현재 작업 디렉터리에서 `.git` 루트 자동 탐색 |

세부 동작 규칙은 다음과 같습니다.

- **상대 경로는 해당 설정 파일(`crex.json`)이 위치한 디렉터리 기준**으로 해석합니다. 현재 실행 위치를 기준으로 삼으면 어느 폴더에서 명령을 실행하느냐에 따라 대상이 달라지기 때문입니다. 덕분에 반입 번들 폴더를 통째로 다른 드라이브로 옮겨도 상대 경로 설정이 깨지지 않습니다.
- **저장소의 하위 디렉터리를 지정하면 자동으로 저장소 루트로 올려 잡습니다.** 예를 들어 `D:\work\myrepo\src`를 지정해도 `D:\work\myrepo`로 정규화합니다. 리포트의 모든 파일 경로와 정적분석 결과는 저장소 루트를 기준으로 맞춰져야 하기 때문입니다.
- **환경변수(`%VAR%`, `$VAR`)와 홈 경로(`~`) 확장을 지원합니다.** `%USERPROFILE%/work/myrepo` 형태로 작성할 수 있습니다.
- 지정한 경로가 존재하지 않으면 즉시 오류를 발생시킵니다. `.git` 폴더가 없는 경우에는 경고를 출력하고 계속 진행합니다 — 전체 감사(`scan`)는 Git 없이도 동작하지만, 변경분 리뷰(`review`)는 Git 저장소가 아니면 실행을 거부합니다.
- 리포트 기본 저장 경로는 `<워크스페이스>/reports`이며, `--out` 옵션이나 `CREX_REPORTS` 환경변수로 변경할 수 있습니다.

CLI, MCP 서버, 관제 화면(`crex.viz`) 세 진입점 모두 `crex/workspace.py`의 동일한 해석 규칙을 공유합니다.

### 실행 중에 대상 저장소 바꾸기

| 실행 환경 | 변경 방법 | 유지 범위 |
|---|---|---|
| 터미널 CLI | `python -m crex workspace <경로>` | `crex.json`에 영구 저장됨 |
| 관제 화면 (`viz`) | 왼쪽 "워크스페이스" 옆 **변경** 버튼 | 관제 서버 프로세스가 실행 중인 동안만 유지 |
| Zed 에이전트 | `set_workspace` 도구 호출 | MCP 서버 프로세스가 실행 중인 동안만 유지 |

관제 화면과 MCP 서버에서의 변경은 설정 파일을 수정하지 않습니다. 한 사용자의 일시적인 화면 조작이나 대화가 다음 실행의 기본 대상까지 바꾸어 놓지 않도록 하기 위함입니다. 영구적으로 고정하려면 CLI 명령을 사용하십시오.

세 경로 모두 시작 시점과 **동일한 경로 검증**을 거칩니다. 존재하지 않는 경로는 거부하고, 하위 폴더는 저장소 루트로 정규화하며, 새 워크스페이스 안에 `crex.json`이 있으면 해당 설정을 자동으로 읽어 들입니다(`--config`나 `--out`으로 명시 고정한 항목은 그대로 유지됩니다).

## `llm.generator` — 지적을 생성하는 모델

```json
{
  "llm": {
    "generator": {
      "base_url": "http://vllm-qwen:8000/v1",
      "model": "Qwen3.6-27B",
      "api_key": "EMPTY",
      "temperature": 0.0,
      "max_output_tokens": 4096,
      "max_input_tokens": 8192,
      "timeout": 120.0,
      "max_retries": 3,
      "structured_output_mode": "auto"
    }
  }
}
```

- `base_url`: `/v1`까지만 입력합니다. 끝에 `/chat/completions`를 붙이지 마십시오.
- `model`: vLLM 기동 시 `--served-model-name`으로 지정한 이름과 정확히 일치해야 합니다. 일치하지 않으면 HTTP 404 오류가 발생하며, 재시도해도 결과가 같으므로 즉시 실패 처리합니다.
- `api_key`: vLLM을 별도 `--api-key` 없이 띄웠다면 어떤 문자열이든 상관없습니다. HTTP 헤더 형식 유지를 위해 기본값으로 `"EMPTY"`를 사용합니다.
- `temperature`: `0.0`으로 고정하십시오. 동일한 코드를 두 번 리뷰했을 때 결과가 달라지면 골든셋 평가와 정밀도 추적이 불가능해집니다.

### 출력 토큰 상한은 청크당 지적 수에 맞춥니다

`max_output_tokens`는 모델이 한 청크에 대해 응답(내부 추론 포함)을 생성할 수 있는 최대 토큰 수입니다. 응답 길이가 이 상한에 도달하면 vLLM 서버는 JSON 문법 완성 여부와 무관하게 그 자리에서 생성을 중단합니다 — 예를 들어 세 번째 지적을 작성하고 네 번째 지적의 `suggestion`에 코드를 인용하던 중이었다면 따옴표가 닫히지 않은 채로 응답이 잘립니다. 청크마다 코드와 지적 길이가 다르므로 **특정 청크만 간헐적으로 실패하는 현상**으로 나타납니다.

CREX는 이처럼 응답이 중간에 잘리더라도 앞에서 온전히 완성된 지적 객체들을 최대한 복구하고, 응답이 잘렸다는 경고를 오류 목록에 기록합니다. 또한 추론(Thinking) 모델을 사용할 때 내부 사고 과정이 토큰을 소진하는 현상을 막기 위해 기본값을 **4,096 토큰**으로 넉넉히 설정해 두었습니다.

```
경고: 오류 1건으로 리뷰가 온전히 끝나지 않았습니다 (생성 1, 검증 0).
  - src/buffer.cpp#1 응답이 잘려 지적 3건만 복구했습니다 — llm.generator.max_output_tokens 를 올리거나 review.max_findings_per_chunk 를 줄이십시오
```

이 경고가 나타나면 `max_output_tokens`를 올리거나 `review.max_findings_per_chunk`를 줄이십시오. 반대로 상한을 넉넉히 높여 두어도 모델은 출력할 내용이 끝나면 즉시 생성을 멈추므로 평소 응답 속도가 느려지지는 않습니다.

### 입력 토큰 상한을 왜 8192 로 두나

Qwen3.6과 Gemma4 모두 최대 256K 컨텍스트를 지원하지만, CREX는 기본 **8,192 토큰**으로 제한하여 운영합니다.

가장 큰 이유는 컨텍스트가 길어질수록 소형 모델의 결함 탐지 정밀도가 떨어지기 때문입니다. ASE 2025 연구에서 프롬프트에 주입하는 검색 예시를 top-1 → top-3 → top-5로 늘렸을 때 BLEU-4 점수가 12.32 → 11.76 → 10.81로 오히려 단조 감소했습니다. 관련성이 낮거나 상충하는 주변 코드가 많이 섞일수록 모델의 주의력이 흐려집니다. 코드 리뷰에서도 함수 하나와 핵심 계약만 보여주면 정확히 결함을 짚어내던 모델이, 수천 줄짜리 파일 전체를 넣으면 엉뚱한 줄을 지적하기 시작합니다.

추론 속도 문제도 큽니다. Qwen3.6은 입력 컨텍스트가 32K에서 128K로 늘어나면 토큰 처리량이 26 tok/s에서 9 tok/s로 급감합니다.

입력 상한을 높이고 싶다면 반드시 [평가](evaluation.md) 환경을 먼저 구축한 뒤 오탐률(FAR) 변화를 측정하며 조정하십시오.

CREX는 컴포넌트별 사전 토큰 예산제(동적 예산 관리)를 통해 시스템 프롬프트, 룰 택소노미(~1,500토큰), 정적분석 결과(~400토큰), Tree-sitter AST 및 호출 흐름 문맥, 그리고 소스 코드 청크가 8,192 입력 토큰 안에 100% 온전히 들어가도록 보장합니다. 소스 코드가 프롬프트 중간에서 잘려 나가는 일은 발생하지 않습니다.

### `structured_output_mode`

vLLM 버전에 따라 구조화 출력(JSON Schema 강제)을 요청하는 API 필드 형식이 다릅니다.

| 설정값 | 동작 방식 |
|---|---|
| `"auto"` | 서버가 지원하는 방식을 자동으로 탐색합니다 (기본값, 권장) |
| `"response_format"` | 최신 vLLM 표준(`response_format`)으로 고정 |
| `"guided_json"` | 구버전 vLLM 확장(`guided_json`)으로 고정 |

`"auto"`로 설정하면 첫 호출에서 아래 순서대로 시도한 뒤, 성공한 조합을 캐싱하여 이후 모든 호출에 즉시 재사용합니다. 따라서 사내 vLLM 서버의 정확한 버전을 몰라도 기본값 그대로 사용할 수 있습니다.

1. `response_format` + 원본 스키마
2. `guided_json` + 원본 스키마
3. `response_format` + 완화 스키마
4. `guided_json` + 완화 스키마

**완화 스키마**는 `maxLength`, `maxItems`처럼 일부 구형 `xgrammar` 백엔드가 처리하지 못하는 제약 키워드만 제거한 스키마입니다. 단, 환각 방어의 핵심인 `enum`(허용 라인 번호 및 룰 ID 목록) 제약은 어떤 경우에도 제거하지 않습니다.

네 가지 조합이 모두 실패하면 해당 엔드포인트로는 신뢰할 수 있는 리뷰가 불가능하므로, 조용히 0건을 반환하는 대신 즉시 오류로 처리합니다 ([종료 코드 3](getting-started.md#종료-코드)). `python -m crex doctor`를 실행하면 구조화 출력이 정상 작동하는지 사전에 검증할 수 있습니다.

### `guided_decoding_backend`

`guided_json` 방식을 사용할 때 함께 전달할 백엔드 이름입니다. 기본값은 빈 문자열(`""`)이며, 비어 있으면 요청에 해당 필드를 포함하지 않습니다.

최신 vLLM은 이 필드를 알 수 없는 키로 간주해 HTTP 400 오류를 반환하므로, 구버전 vLLM에서 백엔드를 명시해야 하는 경우에만 `"xgrammar"` 등으로 설정하십시오.

### `llm.generator.extra_body`

vLLM 요청 JSON 본문에 그대로 병합할 추가 파라미터입니다. 주로 Qwen3.x 계열 모델의 장문 추론(Thinking) 모드를 제어할 때 사용합니다.

```json
{
  "llm": {
    "generator": {
      "extra_body": {
        "chat_template_kwargs": { "enable_thinking": false }
      }
    }
  }
}
```

이 객체 안의 값들은 vLLM 서버로 그대로 전달됩니다(`stop` 같은 배열 파라미터도 배열 형태 그대로 유지되며, `"// ..."` 주석 키만 제거됩니다).

## `llm.verifier` — 지적을 재판정하는 모델

```json
{
  "llm": {
    "verifier": {
      "base_url": "http://vllm-gemma:8000/v1",
      "model": "gemma-4-26b-it",
      "max_input_tokens": 4096,
      "max_output_tokens": 4096,
      "timeout": 60.0
    }
  }
}
```

**생성 모델과 다른 계열의 모델을 사용하는 것이 핵심입니다.** 동일한 모델에게 자신이 방금 생성한 지적을 검증하게 하면 스스로 만든 환각에 다시 동조할 가능성이 높습니다.

검증 단계는 생성 단계보다 연산 부하가 훨씬 가볍습니다. 지적이 발생한 청크에 대해서만 호출되며, 입력은 지적 라인 주변 `±25`줄 윈도우와 연관 심볼 정의뿐이고 출력도 판정(`yes`/`no`)과 짧은 근거 한두 문장입니다. 따라서 GPU 메모리를 상대적으로 적게 배분해도 충분합니다.

만약 `verifier` 블록을 통째로 생략하면 `generator` 설정을 그대로 재사용합니다. 단일 모델 환경에서도 동작하도록 열어 둔 폴백이지만, 가급적 별도 모델을 지정하는 것을 권장합니다.

## `review`

```json
{
  "review": {
    "mode": "native",
    "max_findings_per_chunk": 5,
    "max_workers": 4,
    "require_changed_line": true,
    "min_severity": "low",
    "exclude": ["build/**", "third_party/**"],
    "exclude_rules": ["cpp.c-style-cast", "src/legacy/**:cpp.*"]
  }
}
```

- **`mode`** — 현재 `"native"`만 지원합니다. `"ocr"`을 지정하면 오류를 반환합니다(`alibaba/open-code-review` 연동은 실제 바이너리 스키마 확인 후 추가될 예정입니다).
- **`max_findings_per_chunk`** — 청크 하나에서 생성할 최대 지적 건수입니다. JSON 스키마의 `maxItems`로 강제됩니다. 기본값인 `5`를 넘겨 늘리는 것은 권장하지 않습니다 — 함수 하나에서 5건 이상의 결함이 쏟아진다면 모델이 사소한 의심을 마구잡이로 지적하기 시작했을 가능성이 큽니다.
- **`max_workers`** — 병렬 LLM 호출 스레드 수입니다. vLLM은 연속 배칭(Continuous Batching)을 지원하므로 워커 수를 늘리면 전체 리뷰 속도가 빨라지지만, 여러 팀이 공유하는 GPU 서버라면 기본값 `4` 정도가 적절합니다. HTTP 429나 503 오류가 자주 발생하면 값을 낮추십시오.
- **`require_changed_line`** — diff 리뷰에서 실제로 추가·변경(`added`)된 라인만 지적 대상으로 허용합니다. 기본값 `true`를 유지하십시오. 이를 끄면 변경하지 않은 주변 레거시 코드까지 지적하기 시작해 MR 리뷰의 초점이 흐려집니다. (`scan` 모드에서는 자동으로 해제됩니다.)
- **`min_severity`** — 지정한 심각도 미만의 지적을 최종 리포트에서 숨깁니다. 검증에서 탈락한 기각(`rejected`)과는 다르며, 유효하다고 판정된 지적이라도 현재 리포트에서는 표시하지 않는 필터입니다. 도입 초기에는 `"high"`로 시작하여 신뢰도를 확인한 뒤 `"medium"`이나 `"low"`로 낮추는 방식을 권장합니다.
- **`exclude`** — 리뷰에서 제외할 파일·디렉터리 glob 패턴 목록입니다. 저장소 루트의 `.crexignore` 파일에 적은 패턴과 합산되어 적용됩니다.
- **`exclude_rules`** — 비활성화할 룰 ID 또는 경로 한정 룰 패턴 목록입니다. 전역 제외(`cpp.c-style-cast`)뿐만 아니라 특정 경로에만 룰을 끄는 패턴(`src/legacy/**:cpp.*`, `tests/** rule:any.magic-number`)도 지원합니다. 자세한 문법은 [리뷰 대상 제외](crexignore.md) 문서를 참고하십시오.

## `grounding` — 정적분석

```json
{
  "grounding": {
    "enabled": true,
    "timeout": 120.0,
    "compile_commands_dir": "build",
    "dotnet_project": "src/App.sln",

    "// semgrep_config": "\"semgrep_config\": \"/opt/semgrep-rules\"",
    "// analyzers": "\"analyzers\": [\"cppcheck\", \"ruff\"]"
  }
}
```

사용하지 않는 선택 항목은 삭제하거나 위 예시처럼 키 이름 앞에 `// `를 붙여 주석으로 남겨 두면 됩니다.

정적분석 단계는 LLM 호출 전에 결정론적 분석기를 실행해 객관적 사실을 먼저 확보합니다. 설치되지 않은 분석기는 자동으로 건너뛰며, 어떤 분석기가 실행되었는지는 `-v` 옵션을 붙여 로그에서 확인할 수 있습니다.

- **`compile_commands_dir`** — C++ 리뷰에서 가장 중요한 설정입니다. 이 설정이 없으면 `clang-tidy`가 헤더 경로를 찾지 못해 분석 품질이 크게 떨어집니다. 직접 수동으로 적을 필요 없이 아래 명령을 실행하면 컴파일 DB 생성부터 `crex.json` 경로 등록까지 자동으로 처리합니다.

  ```bash
  python -m crex compiledb
  ```

  CMake와 Visual Studio(MSBuild) 프로젝트를 모두 지원합니다. 상세한 동작 원리는 [정적분석 도구 문서](analyzers.md#compile_commandsjson-이-없으면-반쯤-눈을-감습니다)를 참고하십시오. 값은 파일이 아니라 **디렉터리 경로**이며, 상대 경로는 리뷰 대상 저장소 루트 기준입니다.

- **`clang_tidy_checks`** — 활성화할 체크 패턴입니다. **비워 두는 것이 기본값이자 권장 설정입니다.**

  | 설정 상태 | 적용되는 동작 |
  |---|---|
  | 비워 둠 + 저장소에 `.clang-tidy` 파일 존재 | 프로젝트의 `.clang-tidy` 설정을 그대로 따릅니다 |
  | 비워 둠 + `.clang-tidy` 파일 없음 | 결함 탐지 위주의 내장 기본값(`bugprone-*`, `cert-*`, `clang-analyzer-*` 등)을 사용합니다 |
  | 값을 명시함 | 명시한 체크 목록이 `.clang-tidy`보다 우선 적용됩니다 |

  `clang-tidy`의 명령줄 `--checks` 인자는 프로젝트의 `.clang-tidy` 파일을 덮어쓰므로, 사내 `.clang-tidy` 규칙을 그대로 쓰려면 이 설정을 비워 두십시오.

- **`dotnet_project`** — C# Roslyn 분석기는 프로젝트를 실제로 빌드하며 경고를 수집합니다. 덕분에 팀이 이미 사용 중인 `.editorconfig`와 `Directory.Build.props` 규칙이 별도 설정 없이 그대로 반영됩니다.
  **대부분의 경우 비워 두어도 됩니다.** 비워 두면 변경된 파일이 속한 `.csproj`를 찾아 해당 프로젝트만 빠르게 빌드하고, 여러 프로젝트에 걸쳐 있으면 `.sln`을 빌드합니다. 저장소에 솔루션이 여러 개여서 자동 선택이 불가능할 때만 명시하십시오. 자세한 규칙은 [정적분석 도구 문서](analyzers.md#대상은-알아서-정합니다)에 정리되어 있습니다.

- **`semgrep_config`** — 폐쇄망에서는 `"auto"`가 동작하지 않습니다(외부에서 룰을 내려받으려 시도하기 때문). 반입한 로컬 룰팩 디렉터리나 파일 경로를 지정해야 하며, 비워 두면 Semgrep은 실행되지 않습니다.

- **`analyzers`** — 특정 정적분석기만 선택해 실행하고 싶을 때 이름을 나열합니다. 비워 두면 기본 6종이 모두 활성화됩니다.

  | 이름 | 대상 언어 | 기본 실행 여부 |
  |---|---|---|
  | `clang-tidy` | C++ | 예 |
  | `cppcheck` | C++ | 예 |
  | `roslyn` | C# | 예 |
  | `ruff` | Python | 예 |
  | `mypy` | Python | 예 |
  | `bandit` | Python | 예 |
  | `roslynator` | C# | 아니오 (`analyzers`에 이름을 명시해야 실행됨) |
  | `semgrep` | 공통 | 아니오 (`semgrep_config` 경로가 지정되면 실행됨) |

  분석기 이름에 오타가 있으면 즉시 설정 오류를 발생시킵니다.

## `chunking`

```json
{
  "chunking": {
    "expansion_limit": 4.0,
    "expansion_truncate": 3.0,
    "absolute_max_lines": 150,
    "on_mismatch": "raise"
  }
}
```

diff의 변경 블록(hunk)을 둘러싼 함수 경계까지 확장하되, 거대 함수로 인해 컨텍스트가 폭주하지 않도록 상한을 걸어 분할합니다.

- **`expansion_limit`** / **`expansion_truncate`** — 함수 경계까지 확장한 줄 수가 원본 hunk의 4배(`expansion_limit`)를 초과하면 hunk를 중심으로 위아래 대칭이 되도록 3배(`expansion_truncate`) 길이로 잘라냅니다.
- **`absolute_max_lines`** — 배수와 무관하게 적용되는 청크당 최대 라인 수 상한입니다(기본값 **150줄**). 거대 함수나 인접한 여러 hunk가 합쳐질 때 이 상한을 넘으면 변경 라인 군집을 기준으로 안전하게 독립 청크로 분할합니다.
  - **토큰 예산 자동 연동 (Auto-Clamping)**: 만약 `llm.generator.max_input_tokens`를 작게 설정한 경우에는 토큰 한도에 맞춰 청크 최대 줄 수를 자동으로 하향 조정하여 코드가 잘리는 현상을 방지합니다.
  - **점진적 문맥 압축 (Progressive Pruning)**: 한 줄이 매우 긴 코드가 밀집되어 토큰 예산을 초과하려 할 때는 코드 원문은 보존하고 정적분석 건수·보조 AST 요약·룰 설명을 단계적으로 압축합니다.
- **`on_mismatch`** — diff 내용과 디스크의 실제 파일 내용이 일치하지 않을 때의 동작입니다.
  diff 추출 이후 작업 트리 파일이 수정되면 라인 번호가 모두 어긋납니다. 기본값 `"raise"`는 해당 파일을 안전하게 건너뛰고 오류를 기록합니다. 과거 커밋 간 비교(`--from v1.0 --to v1.1`)를 수행할 때는 대상 커밋 시점으로 체크아웃된 워크트리를 `--workspace`로 지정하십시오.

## 설정 없이 돌리면

`crex.json`이 없어도 기본값(`http://localhost:8000/v1`, `Qwen3.6-27B`)으로 실행됩니다. `doctor` 실행 시 `설정 파일: (없음 — 기본값 사용 중)`으로 표시됩니다.

실제 운영 환경에서는 반드시 `crex.json`을 만들어 사용하는 것을 권장합니다. 실행 로그 첫머리에 적용된 워크스페이스 출처와 설정 요약이 기록되므로 추후 문제 추적이 훨씬 수월해집니다.

```
INFO    crex.cli: 워크스페이스: D:\work\myrepo [--workspace]
INFO    crex.cli: 설정: 모드=native 생성=Qwen3.6-27B@http://vllm-qwen:8000/v1 ...
```
