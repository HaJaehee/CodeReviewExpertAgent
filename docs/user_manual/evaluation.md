# 평가와 튜닝

도입 초기에는 골든셋 구축 과정을 건너뛰고 싶은 마음이 들기 쉽습니다. 과거 MR을 모아 결함 위치를 라벨링하는 작업이 번거롭고, 당장 리뷰 명령은 골든셋 없이도 실행되기 때문입니다.

그러나 골든셋이 없으면 룰을 추가하거나 수정했을 때 리뷰 품질이 실제로 좋아졌는지 나빠졌는지 알 수 없습니다. 검증 필터가 제 역할을 하는지, 입력 토큰 상한을 조정해도 되는지 역시 감에 의존해 판단하게 됩니다.

도입 초기에 일주일만 투자해 골든셋을 구축해 두십시오. 이후 모든 룰 튜닝과 설정 변경의 객관적인 기준점이 됩니다. 전체 도입 일정에서의 위치는 [워크플로](workflow.md#도입-순서) 문서를 참고하십시오.

## 핵심 지표 3가지

- **KBI (Key Bug Inclusion, 재현율)** — 골든셋에 기록된 실제 결함 중 CREX가 찾아낸 비율입니다.
- **FAR (False Alarm Rate, 오탐률)** — CREX가 내보낸 전체 지적 중 틀린 지적(오탐)이 차지하는 비율입니다. **재현율보다 훨씬 중요한 최우선 관리 지표입니다.**
  오탐 1건의 비용은 놓친 결함 1건보다 훨씬 큽니다. 놓친 결함은 동료 코드 리뷰에서 잡힐 여지가 있지만, 오탐은 정상 코드를 두고 개발자가 시간을 허비하게 만들며 결국 도구에 대한 신뢰를 떨어뜨립니다. 지적 건수가 다소 적더라도 내보낸 지적 하나하나가 정확한 편이 훨씬 낫습니다.
- **룰별 정밀도 (Per-Rule Precision)** — 개별 룰이 내보낸 지적 중 정탐의 비율입니다. `counter`를 보강하거나 폐기할 룰을 가려내는 근거가 됩니다.

## 골든셋 만들기

```bash
python eval/run_eval.py init
```

`eval/golden/` 디렉터리와 작성용 템플릿 파일이 생성됩니다.

### 사례 고르기

과거에 완료된 MR 50~100건을 선별합니다. 선정 기준은 다음과 같습니다.

- **실제 리뷰 과정에서 결함이 발견되어 수정된 MR**을 우선적으로 포함합니다. 아무 지적 없이 통과된 MR만 모으면 재현율(KBI)을 측정할 수 없습니다.
- 팀에서 사용하는 언어(C++, C#, Python)를 고르게 섞습니다.
- 파일 수십 개가 한꺼번에 바뀐 대규모 리팩터링 MR은 피하십시오. 라벨링 비용이 지나치게 크고 평가 실행 시간도 길어집니다.
- **결함이 전혀 없는 깨끗한 MR도 20~30% 비율로 함께 포함하십시오.** 문제가 없는 변경에 대해 도구가 침묵을 잘 지키는지가 오탐률(FAR) 측정의 핵심입니다.

### diff 저장

선별한 각 MR의 diff를 파일로 저장합니다.

```bash
git diff <base> <head> > eval/golden/diffs/mr-1234.diff
```

`<base>`는 병합 기준 커밋이며, `git merge-base main <head>` 명령으로 구할 수 있습니다.

### 저장소 스냅숏 준비

CREX는 diff 텍스트만 읽지 않고 디스크의 실제 소스 파일을 함께 읽어 함수 경계와 AST 문맥을 추출합니다. 따라서 **각 MR의 `<head>` 시점 코드가 체크아웃된 디렉터리 경로**가 필요합니다.

가장 깔끔한 방법은 사례별로 `git worktree`를 만들어 두는 것입니다.

```bash
git worktree add ../snapshots/mr-1234 <head>
```

디스크 공간이 부족하다면 평가 실행 직전에 대상 커밋을 순차적으로 체크아웃하는 래퍼 스크립트를 사용해도 됩니다. 기본 설정(`on_mismatch = "raise"`)이 diff와 파일 내용의 일치 여부를 검증하므로, 만약 체크아웃 시점이 어긋나더라도 잘못된 통계가 집계되지 않고 해당 사례만 오류로 기록됩니다.

### 라벨링 작성

`eval/golden/*.jsonl` 파일에 한 줄당 하나의 사례(JSON 객체)를 기록합니다.

```json
{"case_id": "mr-1234", "repo_path": "D:/snapshots/mr-1234", "diff_path": "eval/golden/diffs/mr-1234.diff", "note": "raw 포인터 무효화", "defects": [{"path": "src/buffer.cpp", "line": 16, "category": "code_defect", "severity": "high", "comment": "resize 이후 포인터 무효화", "expected_rule": "cpp.dangling-after-realloc"}]}
```

`defects` 배열에는 **리뷰어가 실제로 지적한 코드 결함만** 넣습니다. 이 라벨링의 일관성이 모든 평가 지표의 신뢰도를 결정합니다.

라벨링에서 제외해야 할 코멘트:

- 단순 칭찬 (`"깔끔한 리팩터링이네요"`)
- 단순 질문 (`"이 부분은 어떤 의도인가요?"`)
- 코딩 스타일·네이밍 코멘트 (`"변수명을 조금 더 명확하게 지어주세요"`)
- 주관적 설계 논의 (`"이 클래스를 둘로 분리하는 건 어떨까요?"`)

라벨링에 포함해야 할 코멘트: **수정하지 않고 배포하면 버그, 크래시, 누수, 보안 취약점 등 실제 문제를 일으키는 결함**만 기록합니다.

`expected_rule`은 선택 항목입니다. 함께 적어 두면 추후 특정 결함을 왜 놓쳤는지 룰 단위로 원인을 분석할 때 유용합니다. 결함이 없는 깨끗한 MR 사례는 `"defects": []`로 비워 둡니다.

빈 줄과 `//`로 시작하는 줄은 파서가 자동으로 무시하므로 주석을 넣어 분류해도 됩니다.

## 지표 해석 방법

### 매칭 허용 범위

CREX가 출력한 지적과 골든셋의 결함이 **같은 파일이면서 라인 번호 차이가 ±3줄 이내**이면 정탐(Hit)으로 인정합니다. 사람 리뷰어도 정확한 한 줄 대신 바로 위아래 줄에 코멘트를 남기는 경우가 많기 때문입니다.

이 허용 오차(±3줄)를 임의로 더 넓히지 마십시오. 범위를 넓히면 엉뚱한 지적이 우연히 근처의 실제 결함과 겹쳐 정탐으로 집계되면서 오탐률(FAR)이 실제보다 낮게 왜곡됩니다. 동일한 결함을 중복 지적하더라도 재현율은 1건으로만 계산됩니다.

### 기각률이 비정상적일 때

- **기각률 40% 미만**: 검증 필터가 제 역할을 하지 못하고 있습니다. 검증 모델이 거의 모든 지적에 `yes`를 반환하고 있을 가능성이 크므로, 리포트 JSON의 `rejected` 배열을 열어 `verdict_no` 기각이 정상적으로 일어나고 있는지 점검하십시오.
- **기각률 70% 초과**: 생성 모델이 과도한 오탐을 쏟아내고 있습니다. 특정 룰의 조건(`criteria`)이 지나치게 모호하거나 프롬프트 설정에 문제가 없는지 확인하십시오.

### 룰별 정밀도 튜닝

정밀도가 50% 미만인 룰은 집중 튜닝 대상입니다.

1. 평가 리포트 JSON에서 해당 룰이 만들어낸 오탐 사례들을 확인합니다.
2. 반복되는 정상 코드 패턴이 보이면 해당 룰의 `counter` 필드에 예외 조건을 추가합니다.
3. 골든셋을 다시 실행해 정밀도와 FAR 변화를 확인합니다.
4. `counter`를 보강해도 정밀도가 50%를 넘지 못하면 해당 룰을 택소노미에서 제거합니다.

단, 총 발생 건수(`emitted`)가 10건 미만인 룰은 표본이 너무 작아 정밀도 수치의 통계적 의미가 부족하므로 판단을 보류하십시오.

## 단계별 수용 기준

| 단계 | KBI (재현율) | FAR (오탐률) | 청크당 지연 시간 |
|---|---|---|---|
| Phase 1 (베이스라인) | 기준치 측정 | 기준치 측정 | 기준치 측정 |
| Phase 2 (룰 튜닝) | ≥ 베이스라인 | ≤ 베이스라인 | — |
| Phase 3 (필터 적용) | 베이스라인의 90% 이상 유지 | **≤ 25%** | ≤ 10초 |

Phase 3(검증 필터 적용)에서 재현율(KBI)이 소폭 낮아지는 것은 정상이며 의도된 현상입니다. 애매한 지적을 엄격히 기각해 재현율을 조금 양보하는 대신 오탐률(FAR)을 25% 이하로 낮추는 것이 검증 필터의 목적입니다.

## 리포트 비교

```bash
python eval/run_eval.py compare reports/phase-1.json reports/phase-3.json
```

```
phase-1.json  →  phase-3.json

  - KBI (재현율)     58.3% →  54.8%  (-3.5%)
  + FAR (오탐률)     19.4% →  11.2%  (-8.2%)
      필터 기각률     51.2% →  58.7%  (+7.5%)

    평균 소요          43.7s →   51.2s
```

`+`는 지표가 개선되었음을, `-`는 하락했음을 뜻합니다. 위 결과는 재현율 3.5%p를 내주는 대신 오탐률을 8.2%p 낮춘 성공적인 튜닝 사례입니다.

## CI 품질 게이트

```bash
python eval/run_eval.py run --max-far 0.25
```

오탐률(FAR)이 `25%`를 초과하면 종료 코드 `1`을 반환합니다. `rules/taxonomy.toml`을 수정할 때마다 이 명령으로 검증하면 저품질 룰이 유입되어 오탐이 늘어나는 일을 방지할 수 있습니다.

## 그다음 — 운영 플라이휠 (Phase 4)

골든셋은 초기 튜닝에는 필수적이지만 수동으로 계속 갱신하기에는 비용이 큽니다. 따라서 안정화 이후에는 실사용 데이터에서 자동으로 얻을 수 있는 보조 지표를 함께 활용합니다.

### Outdated Rate (수정 반영률)

리뷰에서 지적된 라인이 이후 커밋(예: 1주일 이내)에서 실제로 수정되었는지를 측정하는 지표입니다. 별도의 수동 라벨링 없이도 지적의 실질적인 수용도를 대규모로 추적할 수 있습니다(리뷰 결과 JSON을 보관해 두고 `git log -L`과 대조하는 스크립트로 산출 가능).

### 2주 주기 룰 성적표 점검

정밀도와 수정 반영률(Outdated Rate)을 함께 보며 2주마다 룰을 정비합니다. 정밀도는 높은데 수정 반영률이 유독 낮은 룰이 있다면, **"말은 맞지만 개발자가 굳이 고칠 가치를 느끼지 못하는 사소한 지적"**이라는 뜻입니다. 이러한 룰은 `severity`를 낮추거나 과감히 비활성화하는 것이 팀 전체의 리뷰 피로도를 줄이는 길입니다.
