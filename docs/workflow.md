# 워크플로

Zed 에이전트 패널에서 리뷰를 부르는 흐름입니다. 다른 문서가 "어떻게"라면
이 문서는 **"언제 무엇을"**입니다.

준비가 안 됐다면 [운영 문서의 Zed 연동](operations.md#zed-연동-mcp)을 먼저 보세요.

---

## 개발자의 하루

```
코드 작성
   │
   ├─▶ git add
   │      │
   │      └─▶ Zed 에서 "변경사항 리뷰해줘"        ← 여기가 제일 많이 쓰입니다
   │              review_staged
   │
   ├─▶ 지적 대응 / 무시 판단
   │
   ├─▶ git commit
   │
   └─▶ MR 생성
          │
          └─▶ "main 이랑 비교해서 리뷰해줘"
                  review_diff(from_ref="main")
                  → 전체 리포트를 MR 코멘트에 붙여넣기
```

### 커밋 전 자가 점검

```
변경사항 리뷰해줘
```

`review_staged` 가 불립니다. **이 경로가 실제로는 제일 많이 쓰이게 됩니다.**
남이 지적하기 전에 내가 먼저 보는 게 심리적으로 훨씬 편하기 때문입니다.

아직 `git add` 를 안 했다면 "커밋 안 한 거 전부 봐줘"(`review_working_tree`)를
쓰면 됩니다.

### MR 올릴 때

```
main 이랑 비교해서 리뷰해줘
```

`review_diff` 는 **분기점(merge-base)을 자동으로 잡습니다.** 브랜치가 오래됐어도
남이 main 에 넣은 변경이 딸려 들어오지 않습니다. 특정 커밋 두 개를 그대로
비교하려면 "merge-base 쓰지 말고"라고 덧붙이세요.

### 범위 좁히기

큰 변경에서는 모듈별로 나눠 보는 편이 소화하기 좋습니다.

```
파서 폴더 변경분만 리뷰해줘
    → review_staged(paths=["src/parser"])
```

`review_staged` / `review_working_tree` / `review_diff` 셋 다 `paths` 를 받습니다.

### 레거시 훑기

```
이 파일 전체 봐줘          → review_file
파서 폴더 전체 감사해줘     → review_directory
```

diff 가 아니라 코드 전체를 봅니다. 변경 라인이라는 제약이 없어서 **오탐이 눈에
띄게 많습니다.** 정기적으로 돌리지 말고, 낯선 코드를 파악할 때만 쓰세요.

폴더 감사는 대상이 40개를 넘으면 거부합니다. 파일당 LLM 호출이 여러 번이라
비용이 큽니다. 하위 폴더로 나눠 지정하세요.

## 도구 정리

| 이렇게 말하면 | 불리는 도구 | 언제 |
|---|---|---|
| "변경사항 리뷰해줘" | `review_staged` | 커밋 직전 — 가장 자주 |
| "커밋 안 한 거 전부" | `review_working_tree` | add 전에 훑을 때 |
| "main 이랑 비교해서" | `review_diff` | MR 올리기 전 |
| "이 파일 전체 봐줘" | `review_file` | 낯선 파일 파악 |
| "이 폴더 감사해줘" | `review_directory` | 레거시 훑기 |

에이전트가 도구를 안 부르고 **직접 리뷰해 버리는 것**이 가장 흔한 문제입니다.
검증을 안 거친 지적이라 crx 를 쓰는 의미가 사라집니다. 저장소 루트에
[`AGENTS.md`](../AGENTS.md) 를 두면 대부분 해결됩니다 —
[설치 방법](operations.md#에이전트-지시-파일-agentsmd).

그래도 엉뚱한 도구를 고르면 **서버 이름을 직접 부르세요** — "crx 로 리뷰해줘".
27B 급에서는 실제로 자주 있는 일입니다.

## 반환값은 요약입니다

도구가 돌려주는 건 지적 목록 요약이고, 전체 리포트는 파일로 저장됩니다.

```
지적 3건 (높음 1건, 중간 2건)

1. src/buffer.cpp:16 [cpp.dangling-after-realloc] resize() 이후 raw 포인터가 무효화된다
2. ...

전체 리포트: reports/review_staged-001.md
```

전문을 안 돌려주는 건 의도입니다. 도구 반환값은 그대로 에이전트 컨텍스트로
들어가는데, 지적 20건짜리 리포트를 통째로 넘기면 모델의 컨텍스트가 리뷰 결과로
가득 찹니다.

마크다운·SARIF·JSON 세 형식이 `CRX_REPORTS` 경로에 함께 저장됩니다.
MR 코멘트에 붙여넣을 땐 마크다운을 쓰세요.

## 지적을 받았을 때

**이 흐름을 팀에 공유하는 게 도입 성공에 생각보다 큰 영향을 줍니다.** 오탐을
만났을 때 뭘 해야 할지 모르면 그냥 도구를 안 쓰게 되니까요.

```
지적을 읽는다
   │
   ├─ 맞다   ─────────▶ 고친다
   │
   ├─ 애매하다 ───────▶ 지적된 라인을 다시 본다
   │                     └─ 여전히 애매하면 무시해도 됩니다
   │                        (crx 는 확신 없으면 침묵하도록 만들어져 있어서,
   │                         애매한 지적이 나왔다는 것 자체가 신호입니다)
   │
   └─ 틀렸다 ─────────▶ 룰 ID 를 담당자에게 전달
                          (`cpp.dangling-after-realloc` 부분)
```

**오탐 보고에는 룰 ID 가 핵심입니다.** 담당자가 그 룰의 `counter` 필드를 보강하면
같은 오탐이 팀 전체에서 사라집니다.

"리뷰가 이상해요"는 조치할 수 없지만
"`csharp.idisposable-not-disposed` 가 DI 컨테이너 객체를 자꾸 지적해요"는
즉시 조치됩니다.

### 기각률 확인

전체 리포트 하단의 실행 통계를 가끔 보세요.

```
- 생성된 지적: 8건 → 검증 통과 3건 (기각률 62.5%)
```

**40~60% 가 정상**입니다. 벗어나면 파이프라인에 문제가 있다는 신호이니
담당자에게 알려주세요. 너무 낮으면 검증이 일을 안 하는 것이고, 너무 높으면
생성이 헛돌고 있는 겁니다.

## 담당자 작업 (CLI)

아래는 MCP 도구가 없는 영역입니다. 개발자가 아니라 도구 담당자가 터미널에서
합니다.

| 작업 | 명령 | 주기 | 문서 |
|---|---|---|---|
| 상태 점검 | `python -m crx doctor` | 설치·장애 시 | [운영](operations.md) |
| 골든셋 구축 | `python eval/run_eval.py init` | 도입 시 1회 | [평가](evaluation.md) |
| 성능 측정 | `python eval/run_eval.py run` | 룰 변경마다 | [평가](evaluation.md) |
| 룰 추가·폐기 | `rules/taxonomy.toml` 편집 | 2주마다 | [룰 작성법](writing-rules.md) |

### 도입 순서

```
Phase 0  골든셋      1주    ← 건너뛰면 이후가 전부 감으로 굴러갑니다
Phase 1  베이스라인   1~2주   측정만, 아무것도 고치지 않습니다
Phase 2  룰          2~3주   한 번에 하나씩, 매번 재측정
Phase 3  필터        2~3주   FAR ≤ 25% 가 목표
Phase 4  플라이휠     지속
```

Phase 0 을 건너뛰고 싶은 마음이 들 겁니다. 골든셋이 없으면 룰을 추가했을 때
좋아졌는지 나빠졌는지 알 수 없습니다. 절차는 [평가와 튜닝](evaluation.md)에
있습니다.

### 룰 튜닝 루프 (2주)

```
오탐 제보 + 골든셋 재실행 → 룰별 정밀도 확인 (낮은 순)
   │
   ├─ 정밀도 < 50%  ─▶ 오탐 패턴 확인 ─▶ counter 보강 ─▶ 재측정 ─▶ 안 되면 폐기
   │
   └─ 지적 10건 미만 ─▶ 판단 보류 (표본이 작아 통계가 무의미합니다)
```

## 지금 어디에 있나

| 상태 | 다음에 할 일 |
|---|---|
| 아직 설치 전 | [시작하기](getting-started.md) → `doctor` 통과시키기 |
| doctor 통과 | [Zed 연동](operations.md#zed-연동-mcp) 설정 |
| Zed 에서 리뷰가 됨 | Phase 0 — 골든셋 만들기 |
| 골든셋이 있음 | Phase 1 — 베이스라인 측정 |
| FAR ≤ 25% 달성 | 팀 전체 배포 |

현재 프로젝트는 **골든셋이 비어 있고, 실제 LLM 에 한 번도 붙여본 적이 없습니다.**
문서의 품질 수치는 전부 논문에서 온 목표치이지 이 시스템의 관측값이 아닙니다.
