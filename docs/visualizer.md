# 관제 화면

생성 모델과 검증 모델이 실제로 무슨 일을 하는지 웹에서 지켜보는 화면입니다.

```bash
python -m crex.viz
```

띄운 뒤 `http://127.0.0.1:18765` 로 들어가면 됩니다.

## 왜 있나

MCP 서버는 에이전트에게 **요약만** 돌려줍니다. 컨텍스트를 아끼려는 의도된
설계지만, 그 대가로 파이프라인 안쪽이 통째로 보이지 않습니다. 프롬프트를
다듬거나 오탐의 원인을 찾으려면 정확히 그 안쪽이 필요합니다.

- 청크가 어디서 어디까지 잘렸는가
- 정적분석이 그 청크에서 무엇을 보고했는가
- 생성 모델이 **어떤 프롬프트를 받고** 무엇을 뱉었는가
- 검증 모델이 그것을 **왜** 살렸거나 죽였는가

화면의 중심이 지적 목록이 아니라 두 모델의 호출 레인인 이유입니다.

## 화면 읽는 법

### 파이프라인 레일

`청킹 → 그라운딩 → 생성 → 검증` 네 칸이 진행에 따라 켜지고, 끝나면 소요 시간이
남습니다. 그라운딩이 오래 걸린다면 분석기 하나가 타임아웃(기본 120초)까지
버티는 중일 수 있습니다.

### 지표

| 항목 | 뜻 |
|---|---|
| 청크 | LLM 호출 단위. 대체로 변경된 함수 하나 |
| 정적분석 | 도구가 보고해 프롬프트에 실린 사실의 수 |
| 생성된 지적 | 생성 모델이 내놓은 것. 아직 검증 전입니다 |
| 결정론적 기각 | LLM 을 부르지 않고 걸러낸 것 (라인 범위 밖, 중복 등) |
| 검증 기각 | 검증 모델이 근거 부족으로 죽인 것 |
| 최종 유지 | 리포트에 실리는 것 |
| 기각률 | 기각 ÷ 생성. BitsAI-CR 실측 55.25% 가 기준선입니다 |

기각률이 지나치게 낮으면 검증이 일을 안 하고 있다는 뜻이고, 지나치게 높으면
생성 프롬프트나 룰이 헛돌고 있다는 뜻입니다.

### 호출 레인

왼쪽이 생성, 오른쪽이 검증입니다. 카드 하나가 LLM 호출 하나입니다.

**카드를 누르면 그 호출의 전부가 나옵니다** — 시스템 프롬프트, 사용자 프롬프트,
강제된 JSON 스키마, 모델이 뱉은 원문, 파싱된 결과. 지적이 왜 나왔는지 추측할
필요가 없어지는 것이 이 화면의 존재 이유입니다.

스키마 탭에서 `line` 의 `enum` 을 보세요. 그 청크에서 실제로 변경된 라인 번호만
들어 있습니다. 라인 번호 환각이 사후 필터링 대상이 아니라 **생성 단계에서
불가능해지는** 장치가 그것입니다.

### 판정 표

유지된 것과 기각된 것을 한 표에 놓고, 기각에는 사유를 답니다.
`코드가 스니펫에 없음` 이 잦다면 생성 프롬프트가 모델을 지어내게 만들고 있다는
신호입니다. `라인 범위 밖` 은 guided decoding 이 꺼져 있을 때 나타납니다.

### 에이전트가 받는 요약

Zed 의 에이전트 패널이 실제로 받는 문자열 그대로입니다. 관제 화면용으로 다시
만든 것이 아니라 `ReviewService` 의 반환값을 그대로 띄웁니다.

## 실행 기록은 브라우저에 남습니다

서버에는 DB 가 없습니다. 진행 중인 실행의 이벤트만 메모리에 있다가 사라지고,
기록은 브라우저 **localStorage** 에 남습니다. 관제 화면 하나 때문에 폐쇄망 장비에
DB 를 세우고 그 백업·권한·반입 승인을 떠안을 이유가 없습니다.

왼쪽 목록에서 지난 실행을 누르면 그때 화면이 그대로 재생됩니다. 새로고침해도
남아 있고, 브라우저를 바꾸거나 기록을 지우면 사라집니다.

프롬프트는 저장할 때 6,000자에서 잘립니다 (localStorage 는 보통 5MB 라 자르지
않으면 몇 번 만에 꽉 찹니다). 진행 중인 실행에서는 서버가 준 원본을 그대로
보여주므로 잘리지 않습니다.

## 옵션

```bash
python -m crex.viz --port 9000 --workspace D:\work\myproject --config crex.toml
```

| 옵션 | 뜻 | 기본값 |
|---|---|---|
| `--host` | 바인드 주소 | `127.0.0.1` |
| `--port` | 포트 | `18765` |
| `--workspace` | 리뷰 대상 저장소 루트 (`--repo` 는 예전 이름) | 현재 디렉터리에서 git 루트 탐색 |
| `--config` | 설정 파일 | 워크스페이스 → 현재 디렉터리 순 탐색 |
| `--out` | 리포트 저장 위치 | `<워크스페이스>/reports` |
| `--stdlib` | uvicorn 이 있어도 stdlib 서버를 쓴다 | 꺼짐 |

환경변수 `CREX_WORKSPACE`(이전 이름 `CREX_REPO`), `CREX_CONFIG`, `CREX_REPORTS` 도
CLI·MCP 서버와 똑같이 읽습니다. 세 진입점이 서로 다른 저장소를 보고 있으면 화면의
의미가 없으므로 규칙을 한 곳에 모아 뒀습니다 —
[설정](configuration.md#workspace--리뷰-대상-저장소) 참고.

화면 왼쪽 "리뷰 실행" 패널 아래에 지금 보고 있는 워크스페이스·설정 파일·리포트
경로가 그대로 표시됩니다. 워크스페이스에 `.git` 이 없으면 붉게 표시되고, 그때는
diff 리뷰(스테이징·두 참조 비교)는 못 하고 파일·폴더 감사만 됩니다.

### 바인드 주소

기본값은 루프백입니다. 화면에는 **소스 코드 전문과 프롬프트가 그대로** 실리므로,
`--host 0.0.0.0` 은 그 사실을 알고 쓰세요. 인증 기능은 없습니다.

## uvicorn 이 없어도 됩니다

있으면 uvicorn(ASGI)으로, 없으면 표준 라이브러리 `http.server` 로 뜹니다. 동작은
같습니다 — 사용자 한둘이 0.4초마다 이벤트를 받아가는 게 전부라 성능 차이가
의미를 갖지 않습니다.

반입할 wheel 을 늘리고 싶지 않다면 그냥 두세요. 쓰고 싶다면
`requirements-optional.txt` 에 있습니다.

## LLM 없이 화면 확인하기

폐쇄망 반입 직후 vLLM 이 아직 안 떠 있을 때, `tests/fake_vllm.py` 를 띄워 화면만
먼저 확인할 수 있습니다. 파이프라인 전 구간이 실제 HTTP 경로를 타므로 화면이
제대로 동작하는지 판별하는 데 충분합니다.

## 자주 겪는 것

**화면은 뜨는데 실행이 바로 실패한다**
`엔드포인트 점검` 을 눌러 보세요. 두 칩이 빨개지면 vLLM 이 안 떠 있거나 모델
이름이 다릅니다. `python -m crex doctor` 와 같은 점검입니다.

**청크가 0개다**
리뷰할 변경이 없거나, 지원하지 않는 언어이거나, diff 와 작업본이 어긋나
파일이 통째로 건너뛰어진 경우입니다. 마지막 경우는 요약에 오류로 나옵니다.

**호출 카드가 안 생긴다**
청크는 있는데 생성 호출이 없다면 그 언어에 적용할 룰이 없는 것입니다.
`python -m crex.rules` 로 택소노미를 확인하세요.

**중단을 눌렀는데 바로 안 멈춘다**
이미 나간 호출은 응답을 기다립니다. 다음 호출부터 멈춥니다. 중단된 실행도
그때까지의 결과로 리포트를 남깁니다.
