# 워크플로

Zed 에이전트 패널에서 대화형으로 코드 리뷰를 실행하는 흐름을 설명합니다. 다른 문서들이 "어떻게 설정하고 실행하는가"를 다룬다면, 이 문서는 **"언제 무엇을 실행하고 결과에 어떻게 대응하는가"**를 다룹니다.

아직 연동 전이라면 [운영 문서의 Zed 연동](operations.md#zed-연동-mcp)을 먼저 확인하십시오.

---

## 개발자의 하루

```
코드 작성
   │
   ├─▶ git add
   │      │
   │      └─▶ Zed에서 "변경사항 리뷰해줘"         ← 가장 자주 사용하는 단계입니다
   │              review_staged
   │
   ├─▶ 지적 사항 수정 또는 제외 판단
   │
   ├─▶ git commit
   │
   └─▶ MR 생성
          │
          └─▶ "main이랑 비교해서 리뷰해줘"
                  review_diff(from_ref="main")
                  → 생성된 리포트를 MR 코멘트에 첨부
```

### 커밋 전 자가 점검

```
변경사항 리뷰해줘
```

`review_staged` 도구가 호출됩니다. **실무에서 가장 빈번하게 사용되는 경로입니다.** 동료 리뷰어에게 지적받기 전에 본인이 먼저 결함을 찾아 수정하는 것이 훨씬 빠르고 부담이 적기 때문입니다.

아직 `git add`를 하지 않은 상태라면 `"커밋 안 한 거 전부 봐줘"`(`review_working_tree`)라고 요청하면 됩니다.

### MR 올릴 때

```
main이랑 비교해서 리뷰해줘
```

`review_diff`는 **공통 분기점(`merge-base`)을 자동으로 계산합니다.** 브랜치를 분기한 지 오래되었더라도 다른 개발자가 `main`에 병합한 커밋이 섞여 들어오지 않습니다. 두 커밋을 `merge-base` 없이 직접 비교하고 싶다면 `"merge-base 쓰지 말고 비교해줘"`라고 덧붙이십시오.

### 범위 좁히기

변경 규모가 클 때는 디렉터리나 모듈 단위로 나누어 리뷰하는 편이 결과를 검토하기 수월합니다.

```
파서 폴더 변경분만 리뷰해줘
    → review_staged(paths=["src/parser"])
```

`review_staged`, `review_working_tree`, `review_diff` 세 도구 모두 `paths` 인자를 지원합니다.

### 레거시 훑기

```
이 파일 전체 봐줘          → review_file
파서 폴더 전체 감사해줘     → review_directory
```

diff가 아니라 파일 전체 코드를 검사합니다. "변경된 라인만 지적한다"는 제약이 해제되므로 **diff 리뷰에 비해 오탐이 눈에 띄게 늘어납니다.** 일상적으로 실행하기보다 낯선 레거시 모듈을 처음 파악하거나 중점 점검할 때만 사용하십시오.

폴더 감사는 대상 파일이 40개를 초과하면 실행을 거부합니다. 파일당 여러 번의 LLM 호출이 발생하여 소요 시간이 길어지므로, 하위 폴더 단위로 범위를 나누어 실행하십시오.

## 도구 정리

| 사용자 요청 예시 | 호출되는 도구 | 권장 시점 |
|---|---|---|
| "변경사항 리뷰해줘" | `review_staged` | 커밋 직전 (가장 자주 사용) |
| "커밋 안 한 거 전부 봐줘" | `review_working_tree` | `git add` 전에 전체 변경을 훑어볼 때 |
| "main이랑 비교해서 리뷰해줘" | `review_diff` | MR 생성 직전 |
| "이 파일 전체 봐줘" | `review_file` | 낯선 단일 파일의 잠재 결함 파악 |
| "이 폴더 감사해줘" | `review_directory` | 레거시 모듈 점검 |
| "지금 어느 저장소 보고 있어?" | `get_workspace` | 리뷰 대상 경로가 예상과 다를 때 |
| "저쪽 저장소 리뷰해줘" | `set_workspace` | 리뷰 대상 저장소 전환 (아래 참고) |

### 대상 저장소 바꾸기

에이전트에게 다른 저장소 경로를 알려주면 `set_workspace` 도구로 리뷰 대상을 전환합니다.

```
"D:\work\other 저장소 리뷰해줘"
    → set_workspace("D:\work\other")
    → review_staged()
```

**이 변경은 MCP 서버 프로세스가 실행 중인 동안에만 유지됩니다.** `crex.json` 파일은 수정하지 않으므로 Zed를 재시작하면 원래 설정된 저장소로 돌아옵니다. 영구적으로 변경하려면 터미널에서 `python -m crex workspace <경로>`를 실행하거나 `.zed/settings.json`의 `CREX_WORKSPACE` 값을 수정하십시오.

`.git`이 없는 일반 폴더를 지정하면 대상 전환은 되지만 diff 기반 리뷰는 불가능하며, 파일·폴더 전체 감사(`review_file`, `review_directory`)만 사용할 수 있다고 안내합니다.

Zed 연동 시 가장 흔히 겪는 문제는 에이전트가 CREX 도구를 호출하지 않고 **직접 diff를 읽어 임의로 리뷰하는 현상**입니다. 교차 검증을 거치지 않은 추측성 지적이 나오면 CREX를 도입한 의미가 사라집니다. 리뷰 대상 저장소 루트에 [`AGENTS.md`](../../AGENTS.md)를 복사해 두면 대부분 해결됩니다 — 자세한 설정은 [에이전트 지시 파일 안내](operations.md#에이전트-지시-파일-agentsmd)를 참고하십시오.

만약 지시 파일을 두었는데도 에이전트가 도구를 호출하지 않는다면 **"crex로 리뷰해줘"**처럼 도구 이름을 직접 명시해 요청하십시오. 27B 규모 모델에서는 도구 이름을 직접 언급해 주는 것이 훨씬 확실합니다.

## 반환값은 요약입니다

MCP 도구가 에이전트에게 돌려주는 텍스트는 지적 목록의 핵심 요약뿐이며, 상세 리포트 전문은 파일로 저장됩니다.

```
지적 3건 (높음 1건, 중간 2건)

1. src/buffer.cpp:16 [cpp.dangling-after-realloc] resize() 이후 raw 포인터가 무효화됩니다
2. ...

전체 리포트: reports/review_staged-001.md
```

리포트 전문을 반환하지 않는 것은 의도적인 설계입니다. MCP 도구의 반환값은 에이전트 대화 컨텍스트에 그대로 쌓이는데, 지적 20건짜리 상세 리포트를 통째로 넘기면 모델의 컨텍스트가 순식간에 소진되기 때문입니다.

마크다운, SARIF, JSON, HTML 리포트가 `CREX_REPORTS` 경로에 함께 저장됩니다. MR 코멘트에 공유할 때는 마크다운 리포트를, 브라우저에서 상세 내역을 볼 때는 HTML 리포트를 활용하십시오.

## 지적을 받았을 때

**이 대응 기준을 팀 전체에 공유하는 것이 도입 성패를 좌우합니다.** 오탐을 마주했을 때 어떻게 처리해야 할지 모르면 개발자들은 곧 도구를 외면하게 됩니다.

```
지적 내용을 확인합니다
   │
   ├─ 타당한 지적 ───▶ 코드를 수정합니다
   │
   ├─ 애매한 지적 ───▶ 지적된 라인과 주변 문맥을 다시 확인합니다
   │                     └─ 실제 문제가 아니라면 무시하거나 .crexignore에 등록합니다
   │                        (CREX는 확신이 없으면 침묵하도록 설계되어 있으므로,
   │                         애매한 지적이 나왔다면 코드가 오해하기 쉽게 작성되었을 가능성도 있습니다)
   │
   └─ 명백한 오탐 ───▶ 룰 ID를 담당자에게 전달합니다 (`cpp.dangling-after-realloc` 등)
                         또는 관제 화면(viz)에서 [+ 제외] 버튼으로 즉시 제외 규칙에 등록합니다
```

**오탐 제보의 핵심은 룰 ID입니다.** 담당자가 해당 룰의 `counter`(예외 조건) 필드를 한 줄 보강하면, 동일한 유형의 오탐이 팀 전체에서 즉시 사라집니다.

`"리뷰 결과가 이상해요"`라는 제보만으로는 원인을 찾기 어렵지만, `"csharp.idisposable-not-disposed 룰이 DI 컨테이너가 관리하는 객체를 반복해서 지적해요"`라고 알려주면 즉시 조치할 수 있습니다.

### 기각률 확인

리포트 하단의 실행 통계를 가끔 확인해 보십시오.

```
- 생성된 지적: 8건 → 검증 통과 3건 (기각률 62.5%)
```

**기각률 40~60%가 정상 범위**입니다. 이 범위를 크게 벗어나면 파이프라인 설정에 문제가 있다는 신호이므로 담당자에게 공유해 주십시오. 기각률이 너무 낮으면 검증 모델이 제 역할을 하지 못하는 것이고, 너무 높으면 생성 모델이 불필요한 지적을 과도하게 만들고 있는 것입니다.

## 담당자 작업 (CLI)

아래 작업은 MCP 도구가 아닌 터미널 CLI에서 도구 담당자가 수행하는 관리 영역입니다.

| 작업 | 실행 명령 | 권장 주기 | 관련 문서 |
|---|---|---|---|
| 상태 점검 | `python -m crex doctor` | 최초 설치 및 장애 발생 시 | [운영](operations.md) |
| 골든셋 구축 | `python eval/run_eval.py init` | 도입 초기 1회 | [평가](evaluation.md) |
| 성능 측정 | `python eval/run_eval.py run` | 룰 변경 시마다 | [평가](evaluation.md) |
| 룰 추가·폐기 | `rules/taxonomy.toml` 편집 | 2주 주기 | [룰 작성법](writing-rules.md) |

### 도입 순서

```
Phase 0  골든셋 구축   1주     ← 건너뛰면 이후 모든 튜닝을 감에 의존하게 됩니다
Phase 1  베이스라인    1~2주   현재 성능 측정만 수행 (아무것도 수정하지 않음)
Phase 2  룰 튜닝       2~3주   한 번에 하나씩 룰 추가·수정 및 매번 재측정
Phase 3  필터 조정     2~3주   오탐률(FAR) ≤ 25% 달성 목표
Phase 4  플라이휠 운영 지속    정기 지표 점검 및 저품질 룰 정리
```

Phase 0(골든셋 구축)을 건너뛰고 싶은 유혹이 들기 쉽지만, 기준점 역할을 하는 골든셋이 없으면 룰을 고쳤을 때 성능이 개선되었는지 오히려 악화되었는지 판단할 수 없습니다. 구체적인 절차는 [평가와 튜닝](evaluation.md) 문서를 참고하십시오.

### 룰 튜닝 루프 (2주)

```
오탐 제보 취합 + 골든셋 재실행 → 룰별 정밀도 확인 (낮은 순 정렬)
   │
   ├─ 정밀도 < 50%  ─▶ 오탐 패턴 분석 ─▶ counter 보강 ─▶ 재측정 ─▶ 개선되지 않으면 룰 폐기
   │
   └─ 발생 건수 10건 미만 ─▶ 판단 보류 (표본이 작아 통계적 유의성이 부족합니다)
```

## 지금 어디에 있나

| 현재 단계 | 다음 수행할 작업 |
|---|---|
| 설치 전 | [시작하기](getting-started.md)를 따라 설치 후 `doctor` 통과 확인 |
| `doctor` 통과 | [Zed 연동](operations.md#zed-연동-mcp) 설정 및 테스트 |
| Zed에서 리뷰 동작 확인 | Phase 0 — 사내 과거 MR 기반 골든셋 구축 |
| 골든셋 구축 완료 | Phase 1 — 베이스라인 성능 측정 |
| FAR ≤ 25% 달성 | 팀 전체 배포 및 정기 튜닝 루프 운영 |

도입 초기에는 사내 코드베이스에 맞춘 골든셋을 먼저 구축하여 목표 지표(FAR ≤ 25%)를 확인한 뒤 점진적으로 배포 범위를 넓히는 것을 권장합니다.
